## Staged deployment and rollback

1. **Prepare isolated staging.** Use a reviewed schema at the recorded fence with synthetic users, two organizations, owner/editor/analyst/viewer roles, scoped keys, runs and files. Do not replay known-broken historical migrations from empty or copy tenant rows, credentials, cron jobs or live queue state. Use separate Redis, storage, worker queues and application origin; block staging egress to production callbacks. Configure the browser's staging URL/public-key pair and the platform's staging URL. Set the protected browser-session issuer row to that deployment's authentication issuer.
2. **Provision before accepting traffic.** Configure APP_SESSION_JWT_SECRET with the staging project's accepted HMAC signing key, plus isolated Upstash credentials. Keep all signing/service secrets server-side. Verify PostgREST accepts approved-user subjects without requiring GoTrue user rows; confirm issuer/audience/expiry rejection and the shared client's ordinary RPC/table/storage requests. No anonymous identity fallback is acceptable.
3. **Accept end to end.** Apply all eleven migrations, then deploy the matching edge bundle, private worker broadcasts and browser release. Exercise login, reload, logout, expiry, suspension, forced password change, public catalogs and every legitimate role. Exercise forged actors, expired credentials, cross-organization and mismatched project/run IDs, limiter/resolver failures, scoped personal/org keys and scheduled internal calls. Verify real signed URLs and private Realtime joins, including suspension/revocation of already-connected subscribers. If the broker caches authorization beyond suspension, protection is not accepted until bounded/revoked safely.
4. **Coordinate the production cutover.** Resolve the existing hard-gate failures before release. Track the dependency advisories through a separate reviewed update. Preserve approved-user IDs/password hashes and role matrices. Use a controlled maintenance/re-authentication window so old cached clients cannot compute or write against a partially upgraded backend. Provision secrets and verify the issuer before the coordinated SQL/edge/browser/worker cutover; then reopen only after normal signed-session requests work for legitimate users. Public catalogs and explicitly authorized service jobs remain available. Do not use deployment-trigger files as a verification mechanism.
5. **Verify protection after deployment.** Record the applied migration fence, deployed source revisions and effective grants/policies in §16. Use dedicated synthetic staging/acceptance fixtures for negative tests, never arbitrary production tenants. Only mark D309–D312 closed after real gateway, Storage, Realtime, role and actor acceptance succeeds. A green source test or successful deploy alone does not establish deployed protection.
6. **Rollback without reopening identity holes.** Keep a known matching hardened browser/edge bundle and a deployment backup before cutover. If acceptance fails, retain protected-operation maintenance mode and restore the matching bundle/configuration or forward-fix with a new SQL migration. Do not restore anonymous writes, GUC identity fallback or public privileged EXECUTE for availability. Do not drop author columns, audit history, snapshots or results. Stop on a partial migration failure, record the actual fence and repair transactionally before reopening. Reverting this PR wholesale after deployment would restore the vulnerabilities and is not a safe operational rollback.

Remaining acceptance risks are platform signing-key compatibility/rotation, configuration/Redis availability, private broker revocation behavior and the unknown bodies of the eight service-only legacy RPCs. Existing dependency advisories and baseline gate failures are separate unresolved risks. Nothing in this document claims those risks have been deployed away.
